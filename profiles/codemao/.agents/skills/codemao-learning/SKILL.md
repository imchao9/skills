# Codemao Learning

按以下六门顺序处理当前 Codex 对话。学习总结和过程文档各用自己的契约；过程文档不得改变学习总结的生成规则。

## 资格门

完整读取 `references/resolution-contract.md` 后再判断。只使用当前 Codex 对话和当前工作区；能从代码、diff、测试或项目文档发现的证据直接检查，不向用户询问。仅在机制依据确有需要时浏览官方文档或其他一手资料。

仅为学习总结执行契约资格判断。符合资格时，继续按原规则生成学习总结；不符合时，说明依据并只跳过学习总结，不结束本次运行。过程文档不受这项资格判断影响。

**完成标准：** 学习总结的生成或跳过结论已有证据，跳过原因已说明。

## 草稿门

完整读取 `references/process-contract.md`。学习总结符合资格时，再完整读取 `references/teaching-contract.md`，并继续以 `references/resolution-contract.md` 为该文件的格式、分类和结构单一事实源。

运行 `git config user.name` 确定提交人；仅在结果缺失时询问。按 `Asia/Shanghai` 的创建日期，在独立临时目录中创建草稿并冻结日期：

- 学习总结符合资格时，严格按原有两个契约创建一份 UTF-8 Markdown 学习包。
- 无论学习总结是否生成，都严格按过程契约创建一份独立的 UTF-8 Markdown 过程文档。

两个原始草稿完成各自契约检查后，完整读取 `references/humanizer-zh.md`，原样应用其中规则重写所有自然语言正文。不得改写 frontmatter、固定标题、代码、命令、引用、Mermaid、技术事实或验证状态，不输出 Humanizer 评分或修改说明。重写后重新执行各自契约的全部完成检查。

**完成标准：** 应生成的每份草稿均通过自己的内容、格式和 Humanizer 后置检查；文件互不读取主题或正文。

## 内容门

逐份展示完整 Markdown 和临时路径，并分别询问是否准确、满意。学习总结存在时先确认它，再确认过程文档。

用户指出不准确之处时，只修订对应文件，不重新核验；重新执行该文件的 Humanizer 与完成检查，展示完整草稿并重复确认。用户认为不准确但拒绝指出具体问题时，警告该文件仍有未解决的不准确内容，并要求其明确选择继续或取消；选择继续只通过该文件的内容确认，不构成发布授权。

**完成标准：** 每份草稿都已单独展示，并分别获得满意确认或风险警告后的继续确认。

## 安全门

逐份扫描最终草稿。删除密钥、令牌、密码、Cookie、私钥等凭证，且永不发布其原始形式；个人、客户和生产数据默认脱敏；对含义或敏感性不明确的内部标识询问用户。

任何安全处理导致内容变化时，重新执行对应文件的 Humanizer 与完成检查，展示修改后的完整草稿，并只让该文件返回内容门。

**完成标准：** 每份待发布文件的确切版本都不存在未解决、会阻止发布的敏感数据。

## 发布门

列出本次待发布的全部文件，统一询问用户是否明确授权发布。此前对任一文件的“满意”“继续”或其他确认均不授权发布。

授权前不得读取 GitLab 配置，不得克隆、提交或推送。

**完成标准：** 用户已明确授权发布列表中每份文件的当前安全版本。

## 完成门

获得授权后，读取 `references/gitlab-target.json`；运行 `python3 scripts/publish.py --help` 获取发布器参数与行为，再按确认列表逐份以最终草稿和提交人调用发布器。

每份文件独立沿用现有冲突策略。过程文档改名时必须保留`-过程`后缀。自动重试三次仍冲突时，询问用户开始新一组三次尝试还是取消。

逐份报告发布状态。某份文件失败时，报告原始错误消息和保留的草稿路径；不撤销已经成功发布的其他文件，不得改用分支、Merge Request 或强制推送。

**完成标准：** 每份成功文件都由发布器退出 0，并报告状态、目标路径和 commit；退出 3 继续该文件的冲突处理，任何其他结果只表示该文件未完成。
