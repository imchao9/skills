# refactor: 调整灵犀·需求方案以支持组内推广

## 概览

把“灵犀·需求方案”从偏重审计和交付治理的流程，调整成更适合组内日常使用的需求收集 skill。核心目标是保留能减少实现偏差的能力，同时删除或降级会造成不必要阻塞、重复提问、规则冲突的部分。

## 问题背景

当前 skill 本身有价值，尤其是需求理解校准、来源选择、复杂逻辑场景清单这些部分。但审阅发现它在组内推广前有几类风险：

- 部分 Hard 门禁和模板、后续对话流程互相冲突。
- 即使需求内容已经说明清楚，流程仍会固定追问多个问题。
- skill 内包含单独的 `功能清单模式`，范围已经超出普通需求收集。
- `references/cases.md` 和 `references/tech-template.md` 有时比 `SKILL.md` 施加了更严格的隐藏规则。
- 推广文档缺少给同事直接复制使用的最小成功路径。

## 需求追踪

- R1. 保留显式 `$lingxi-plan` 触发，以及多来源时必须选择来源的安全边界。
- R2. 保留技术方案生成前的需求理解校准。
- R3. 保留复杂逻辑场景清单，以及新增的“是否需要补充场景”确认。
- R4. 消除 `SKILL.md`、`references/tech-template.md`、`references/cases.md`、`agents/openai.yaml` 之间的冲突。
- R5. 降低简单需求中的强制对话和强制落盘成本。
- R6. 删除不适合组内推广的内部一次性样例和过度规则。
- R7. 提供更清晰的同事入口说明和最小示例。

## 范围边界

- 本计划当时不调整“灵犀·代码实现”。
- 本计划不实现新的钉钉 MCP 集成。
- 本计划不创建独立的 `功能清单模式` skill，只负责从“灵犀·需求方案”中移除或抽离这部分规则。
- 本计划不通过真实钉钉读取来验证重写后的 skill。

### 后续独立任务

- 如果组内仍需要 `功能清单模式`，后续单独创建一个“功能清单生成技术方案”的 skill。
- 等确认组内钉钉 MCP 配置后，再补充具体工具名和环境启用说明。

## 上下文与调研

### 相关文件

- `SKILL.md`：主流程、输入契约、门禁、输出契约。
- `references/tech-template.md`：技术方案模板和接口契约要求。
- `references/cases.md`：预期行为、通过样例和失败样例。
- `agents/openai.yaml`：入口提示和触发策略。

### 使用的审阅结论

- 组内可用性审阅：部分交付缺字段直接失败，与后续 R-id 选择流程冲突；接口 Hard 门禁与模板不一致；输出契约缺少中间态。
- 流程风险审阅：高影响假设可能绕过确认；`stage_gate=requirements_captured` 混用了需求状态和技术方案状态；影响范围要求真实代码扫描证据，但普通模式没有扫描步骤。
- 冗余审阅：删除真实测试 case，删除或拆出 `功能清单模式`，删除风险分级硬门禁，降级强制落盘和固定五步对话。

## 关键技术决策

- 以 `SKILL.md` 作为唯一主规则；模板和 cases 只能支撑主规则，不能新增隐藏门禁。
- 把二元的 Hard / Fail 行为改成三档：`必须`、`按需`、`建议`。
- 拆分“中间待确认态”和“完成态”的输出契约。
- 保留“场景补充确认”作为复杂逻辑的必需动作，但避免简单需求默认展示完整场景表。
- 减少重复 cases，保留更少但更有代表性的通过和失败样例。

## 未决问题

### 计划阶段已决

- 是否保留“是否需要补充场景”？保留。它能直接降低复杂分支遗漏风险。
- `功能清单模式` 是否继续留在“灵犀·需求方案”中？不保留。它范围过大，应从推广版中移除，或后续拆成独立 skill。

### 延后到执行阶段

- 简化后的 `default_prompt` 具体措辞，等 `SKILL.md` 瘦身后再微调。
- 原始需求留存默认开启还是默认可选，可在组内试跑一两次后再定。

## 实施单元

- [x] **单元 1：统一流程状态和门禁**

**目标：** 消除会导致 skill 过早失败或过早宣称完成的规则冲突。

**关联需求：** R2、R4、R5

**依赖：** 无

**文件：**
- 修改：`SKILL.md`
- 修改：`references/cases.md`

**方案：**
- 把“部分交付缺少 `本期要做/本期不做`”从 `fetch_status=failed` 改成：当已有 `需求清单` 时，进入交互式范围选择。
- 明确缺少 `developer_notes` 不代表需求读取失败；它应通过对话收集，或在完成前标成明确状态。
- 增加高影响假设门禁：影响范围、数据写入、接口行为、时间规则、权限、验收的问题，只有用户明确同意“按假设推进”后才能继续。
- 拆分状态字段：
  - `requirements_stage_gate: captured | failed`
  - `technical_plan_status: generated | pending | failed`
  - 只有需求已捕获且技术方案已生成时，才推荐交给“灵犀·代码实现”。
- 增加待确认状态的中间输出契约。

**参考模式：**
- 沿用 `SKILL.md` 中已有的显式来源选择逻辑。
- 沿用已有 `需求理解状态`，但把假设处理收紧。

**验证场景：**
- 用户说“只做一部分”但没给 `本期要做/本期不做` 时，进入 R-id 选择，而不是读取失败。
- 高影响不确定项没有获得用户同意时，保持 pending。
- 需求已落盘但技术方案待确认时，不推荐交给“灵犀·代码实现”。

**验收方式：**
- 需求条目已生成后，不再有规则把缺范围字段定义为读取失败。
- 输出契约同时包含 pending 形态和 completed 形态。

- [x] **单元 2：对齐技术模板和实际门禁**

**目标：** 确保按 `references/tech-template.md` 生成的方案，不会天然违反声明的 Hard 要求。

**关联需求：** R3、R4、R5

**依赖：** 单元 1

**文件：**
- 修改：`references/tech-template.md`
- 修改：`SKILL.md`
- 修改：`references/cases.md`

**方案：**
- 明确最终接口契约分级：
  - 新增或改造接口必填：URL、Method、Auth、请求字段、响应字段、错误码。
  - 当接口涉及写入、副作用、跨服务调用或外部消费时，补充：幂等策略、超时与重试、请求示例、响应示例。
- 更新简版和完整版模板，使模板字段与上述规则一致。
- 删除“风险分级表”作为硬失败条件；保留轻量风险评估，高风险需求再使用表格。
- 保留复杂逻辑的场景补充确认，但简版模板只提示“复杂逻辑时填写场景清单”，不要默认展开完整表格。

**参考模式：**
- 沿用 `references/tech-template.md` 已有的通俗表达风格。

**验证场景：**
- 简单只读接口没有副作用时，可以不写幂等策略。
- 写入接口包含幂等策略和超时重试。
- 简单需求有风险说明即可，不需要 P0/P1/P2 分级表。
- 复杂逻辑在接口和数据方案前包含 `场景补充确认`。

**验收方式：**
- 模板字段与 cases 描述的是同一套要求。
- 不存在“模板没要求，但 case 因缺字段判失败”的情况。

- [x] **单元 3：移除或抽离过宽的功能清单模式**

**目标：** 让“灵犀·需求方案”聚焦需求收集和技术方案草稿生成。

**关联需求：** R4、R6

**依赖：** 单元 1

**文件：**
- 修改：`SKILL.md`
- 修改：`references/tech-template.md`
- 修改：`references/cases.md`

**方案：**
- 从“灵犀·需求方案”推广版中移除 `功能清单模式`，或替换成一句提示：“功能清单生成技术方案请使用独立 skill”。
- 删除“一功能点一接口”的规则。
- 删除只服务于功能清单模式的 cases。
- 如果保留占位说明，则改成“每个功能点映射到一个实现项”，实现项可以是新增接口、既有接口改造、任务、配置或数据处理，不强制是 API。

**参考模式：**
- 沿用显式触发边界：只有用户明确使用 `$lingxi-plan` 时才进入。

**验证场景：**
- 普通“灵犀·需求方案”流程不再引用功能清单模式。
- 模板不再要求接口数量等于功能点数量。

**验收方式：**
- 搜索 `功能清单模式` 和 `接口数量必须`，不应再出现有效推广规则。

- [x] **单元 4：简化落盘和对话行为**

**目标：** 让 skill 适合日常需求，而不是每次都按审计级流程执行。

**关联需求：** R5、R7

**依赖：** 单元 1

**文件：**
- 修改：`SKILL.md`
- 修改：`references/cases.md`

**方案：**
- 把固定五步对话改成按需触发：
  - 需求理解校准始终执行。
  - 第三方对接仅在内容不清楚或出现集成信号时询问。
  - 实现范围仅在用户表示部分实现，或需求条目范围不清时询问。
  - 参考模板仅在用户提到类似实现、参考案例或复用诉求时询问。
- 原始需求留存降级为建议或按来源决定：
  - 钉钉来源：建议留存原始需求。
  - 本地方案来源：可选留存。
- 保留技术方案作为主要交付给“灵犀·代码实现”的落盘文件。
- 如果仍保留 `需求收集单` 章节，修正其持久化规则缩进。

**参考模式：**
- 沿用已有 `澄清检查项（可选）` 的原则：不机械提问。

**验证场景：**
- 需求内容已明确无第三方时，不再额外询问第三方。
- 用户已经给出完整范围时，不再重复要求 R-id 选择。
- 简单本地方案输入可以不强制生成原始快照。

**验收方式：**
- 流程中统一使用“仅当不清楚或影响范围时才询问”的表达。

- [x] **单元 5：清理 cases 并补充推广示例**

**目标：** 把 `references/cases.md` 从大型内部测试矩阵，调整成可维护的推广行为参考。

**关联需求：** R4、R6、R7

**依赖：** 单元 1-4

**文件：**
- 修改：`references/cases.md`

**方案：**
- 删除包含真实钉钉链接和真实需求名的 case。
- 删除或合并重复 cases：来源选择、输出顺序、场景清单、风险分级、可执行断言。
- 保留紧凑覆盖：
  - 钉钉 URL 成功、兜底、失败。
  - 仅本地方案、混合来源选择。
  - 需求理解已确认、待确认。
  - 部分范围选择。
  - 复杂场景清单与补充确认。
  - 完成态输出契约。
  - 待确认态输出契约。
- 增加 2-3 个端到端同事示例：
  - 钉钉 URL 模式。
  - 本地方案模式。
  - 混合来源模式。

**参考模式：**
- 沿用现有 pass/fail case 格式，但减少数量。

**验证场景：**
- 新同事可以复制一个示例输入，并理解预期响应。
- cases 不包含内部真实需求名或真实链接。

**验收方式：**
- `references/cases.md` 看起来像短行为指南，而不是容易互相冲突的长测试套件。

- [x] **单元 6：重写组内推广入口提示**

**目标：** 让 skill 在 UI 里容易理解，也不容易误用。

**关联需求：** R1、R7

**依赖：** 单元 1-5

**文件：**
- 修改：`agents/openai.yaml`
- 修改：`SKILL.md`

**方案：**
- 缩短 `default_prompt`，只保留核心承诺：
  - 读取钉钉或本地方案。
  - 校准需求理解。
  - 生成给“灵犀·代码实现”使用的技术方案。
  - 只追问高影响缺失信息。
- 把长示例移到 `SKILL.md` 或 `references/cases.md`。
- 保留 `allow_implicit_invocation: false`。

**参考模式：**
- 当前显式调用策略。

**验证场景：**
- 入口提示足够短，能在 UI 中快速扫完。
- 入口提示不重复展开来源选择、输出顺序等详细规则。

**验收方式：**
- `agents/openai.yaml` 只包含简洁入口提示，不包含与 `SKILL.md` 冲突的隐藏行为。

## 全局影响

- **Skill 行为：** 减少错误失败、减少机械追问、交接状态更清楚。
- **生成文档：** 简单需求的技术方案更轻，复杂需求仍保留结构化约束。
- **组内采用：** 新同事有更清晰的示例和更少流程负担。
- **灵犀·代码实现交接：** 交接更安全，因为它依赖“需求已捕获 + 技术方案已生成”两个状态，而不是一个含义过载的 `stage_gate`。

## 风险与依赖

| 风险 | 缓解方式 |
|------|----------|
| 删除过多导致质量下降 | 保留需求理解校准和复杂逻辑场景清单作为风险需求的必需动作。 |
| 降级接口字段导致 API 风险被忽略 | 对写入、有副作用、外部消费的接口触发完整契约。 |
| 清理 cases 时删掉有用边界 | 每类行为保留代表性的通过和失败样例。 |
| 组内仍需要功能清单模式 | 后续拆成独立 skill，不继续塞在“灵犀·需求方案”里。 |

## 建议执行顺序

1. 单元 1：统一流程状态和门禁。
2. 单元 2：对齐技术模板和实际门禁。
3. 单元 3：移除或抽离功能清单模式。
4. 单元 4：简化落盘和对话行为。
5. 单元 5：清理 cases 并补充同事示例。
6. 单元 6：重写入口提示。

## 文档与运营说明

- 调整完成后，用一个钉钉风格输入和一个本地方案输入做人工 dry run。
- 找一位同事不看额外说明，直接试用新的默认提示；根据困惑点微调示例。
- 执行本计划时，最终回复里保留一段简短 changelog，因为这次改动主要是流程行为变化。
