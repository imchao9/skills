# 访谈指南

## 问题顺序

按照依赖关系依次解决问题。可访问材料中已经明确的事实应直接跳过，不再询问。

1. **文档边界**：确认这是一份需求立项说明，而不是完整的实施级 PRD。
2. **业务负责人和截止时间**：由谁执行或负责、为谁服务，以及何时完成。
3. **当前现状**：现有流程、工作量、频率、耗时、错误/返工情况和已知风险。
4. **问题优先级**：当前阶段必须优先解决哪个现有问题。
5. **整体目标**：期望长期实现的业务结果。
6. **当前阶段**：覆盖的对象/场景、明确排除项、与旧流程的关系和兜底方案。
7. **后续阶段**：暂缓范围，以及进入下一阶段的条件。
8. **收益**：基线、目标值、计算依据或衡量计划。
9. **验收**：可观察结果、准确性/完整性、异常行为、运行时长和通过门槛。
10. **条件模块**：存在表格型输出时，表格规则为必选；检测到相关信号时，再提供流程模块和数据接入模块供用户选择。

每轮只问一个问题。使用以下表述格式：

```text
第 N 问：<一个可决策的问题>

我的推荐：<推荐答案及简短理由>

<请用户确认或修正>
```

不要用列表伪装多个子问题。只有当用户需要判断是否采用某个完整模块或规则集时，才可以使用列表。

## 冲突处理

只有当两项陈述不可能同时成立时，才将其视为冲突。应展示相关证据，并询问哪一项具有权威性。典型冲突包括：

- 当前阶段排除了某个系统，但目标中又包含该系统的数据；
- 试点范围数量与列出的对象数量合计不一致；
- 目标比验收范围更严格或更宽泛；
- 两个章节使用了不同的基线、截止时间或阈值；
- 某项收益假设当前阶段已经具备后续阶段才会提供的能力。

不要把同义词或编辑措辞差异视为冲突。可提出一个统一术语；只有当区别会改变含义时，才需要询问用户。

## 草稿状态

### 讨论稿

- 根据已有事实立即生成。
- 将每个重要信息缺口标记为 `[待确认：具体问题]`。
- 将每个尚未被接受的建议答案标记为 `[建议，待确认：具体建议]`；不得将其表述为已经约定的范围、规则、阈值、责任人或排除项。
- 在不同章节中保持相同状态：在用户确认前，建议的排除项或规则在目标、收益和验收标准中都必须保持“建议”状态。
- 可以包含尚未解决但不阻碍推进的事项。
- 绝不能把假设表述为已确认事实。

### 正式稿

以下内容必须得到用户明确确认：

- 背景和核心问题；
- 当前阶段的范围内与范围外边界；
- 整体目标和当前阶段目标；
- 与旧流程的关系和兜底方案；
- 当前阶段通过条件；
- 所有重要矛盾。

只有在责任人和解决时间清晰可见时，才允许保留不阻碍定稿的信息缺口。

## 可选模块触发信号

当需求涉及审批、工单、任务、状态变化、驳回、撤回或多角色交接时，提供 `流程与规则` 模块。

当需求涉及自动采集、导入、定时任务、同步、重试、补数，或数据不完整时必须停止生成结果，提供 `数据接入与运行保障` 模块。

如果用户拒绝，记录 `本次未展开：<模块名>`，然后继续。不要把任何一个可选模块设为转为正式稿的必要条件。
