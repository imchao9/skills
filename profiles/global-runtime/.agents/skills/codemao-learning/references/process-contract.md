# 关键过程文档契约

> 来源：已批准的 `codemao-learning` 过程文档设计。用途：作为过程文档生成资格、内容边界、正文结构与命名格式的单一事实源。

## 生成与证据

每次运行都生成一份过程文档。它独立于学习总结；即使没有高价值、可迁移的技术点，仍须提炼本次开发对话。

用当前对话还原需求、讨论、判断和处理过程；用当前代码、Git diff、测试和项目文档确认最终技术方案。对话中的旧方案或被否决建议，只有在影响关键判断时才写入，并明确标注“曾考虑但未采用”。证据冲突或不足时直接说明，不补写结论。外部资料只在本次开发确实使用或解释机制所必需时引用。

过程文档提炼重点，不逐字转录对话。保留影响方向或结果的需求变化、用户反馈、判断依据、有效证据、重要问题处理与实际发生的验证；省略常规命令、重复确认、无影响的讨论和机械修改。

## 正文结构

正文按以下顺序组织：

1. `需求与背景`
2. `技术方案`
3. `关键判断与处理`

`需求与背景`和`技术方案`必须存在。`关键判断与处理`只在存在非显然判断、方案取舍、问题处理或改变实现的用户反馈时保留；没有实质内容时省略，不写“无”或用套话填充。

不得添加独立的`实施过程`、`完成情况`、`验证与结果`或`未决事项`章节。实际发生的验证、上线或用户反馈写入相关内容，不为不存在的情节创建章节。

## 技术方案

直接说明最终采用的设计，包括确有必要的数据结构、接口、核心流程、异常处理和兼容方式。

- 流程含三个以上相互依赖的步骤、分支或异常路径，且图比文字更清楚时，使用 Mermaid；简单流程直接用文字。
- 优先摘录工作区中实际采用的最小代码片段，标明语言及对应文件或方法。代码过长时只保留与方案有关的部分。
- 尚未形成代码时可以使用伪代码，但必须明确标注“伪代码”；不得根据印象补写看似真实的代码。
- Humanizer 只处理自然语言，不改写代码、命令、引用或 Mermaid。

不设字数或阅读时长。每段必须说明需求背景、技术方案或关键判断；合并重复讨论。简单需求写短，复杂需求按实际需要展开。

## Frontmatter 与命名

仅复用 `resolution-contract.md` 的 frontmatter 字段、日期、提交人、中文主题和规范化规则；不复用其中的资格、主题分类或正文结构。

文件名固定为 `yyyy-MM-dd-{中文主题}-过程.md`。frontmatter `title` 必须是相同的`{中文主题}-过程`；`topics`包含一至三个根据过程文档自身内容生成的中文技术主题，不读取或复用学习总结的主题。

日期取 `Asia/Shanghai` 的创建日并在创建后冻结。发生文件名冲突时沿用现有策略；自动生成的新中文主题必须保留`-过程`后缀。

## 完成标准

过程文档仅在以下条件全部满足后完成：已经提炼当前开发对话；正文包含`需求与背景`和`技术方案`，可选章节符合保留条件和顺序；内容没有对话流水账或无依据的技术结论；图、代码和伪代码符合使用条件；frontmatter 与文件名符合本契约；主题来自过程文档自身；Humanizer 处理后仍通过上述检查。
