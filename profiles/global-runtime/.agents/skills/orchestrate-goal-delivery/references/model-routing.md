# 模型路由

按不确定性、爆炸半径、可逆性和反馈闭环强度路由。先满足质量底线，再考虑时延和成本。分配模型前始终检查当前运行时可用的模型与角色列表。

| 工作形态 | 首选层级 | 典型推理强度 | 独立角色 |
|---|---|---|---|
| 外部契约、协议推断、数据迁移、并发、鉴权、跨模块状态机 | 最强前沿能力 | 高至最高 | 可用时使用 reviewer 与 verifier |
| 契约清晰、API/UI/store 边界受控的垂直产品切片 | 均衡 agentic 能力 | 中至高 | 面向用户或数据敏感时使用 verifier |
| 只读探索、文件盘点、机械改写、聚焦测试、文档 | 快速或低成本能力 | 低至中 | 可选 |
| 多 Agent 的最终集成 | 最强前沿能力 | 高 | 与实现者不同的 verifier |

当运行时提供 `sol`、`terra`、`luna` 等模型族时：

- 最强前沿行使用 `sol` 级能力；
- 有边界的实现使用 `terra` 级能力；
- 快速探索和机械工作使用 `luna` 级能力；
- 若专用 `reviewer` 或 `verifier` 角色已固定适当模型和推理等级，优先使用该角色，不要手动按模型名替代。

这些名称只是示例，不是永久白名单。若可用模型或推理等级变化，保留层级决策并选择当前等价能力。

## 路由检查

派工前回答：

1. 是什么不确定性让这张票据困难？
2. 若实现错误，爆炸半径有多大？
3. 错误实现有多容易回滚？
4. 测试或可观察检查能多快、多可靠地暴露错误？
5. 工作属于生成、机械执行，还是独立验收？
6. 模型是否需要继承原始上下文，还是使用精简新鲜简报更安全？
7. 相比继承父模型，覆盖模型是否有具体的质量、时延或成本收益？

如果没有答案足以证明覆盖模型有益，则继承父模型。
