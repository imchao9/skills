# 分批交付编排

当目标已足够清晰、可以执行时，管理交付 frontier（前沿）。主 Agent 始终负责协调与集成；有边界的 worker 只处理已解除阻塞的交付切片。

本 skill 拥有**模型路由、批次、派工、监督、集成和验收**。它不替代产品探索，也不以发布 tracker 票据为主要职责。

不适用于没有有效拆分空间的小改动。不要为了看起来并行而创建 Agent。

## 1. 判断工作是否已可编排

先读取仓库指令、当前实现，以及已确认的 spec、计划或票据；在安排任何执行前判断输入状态：

- **仍有决策迷雾：** 关键问题尚不能表述为稳定的交付结果。暂停编排，改用可用的探索或 wayfinding 流程。
- **路线清楚但票据缺失或有争议：** 使用可用的拆票流程起草、确认并发布垂直票据。创建外部 issue 仍需要授权。
- **票据可执行：** 每张票据都具备结果、真实阻塞边、验收标准和所需外部门禁。进入本 skill。

若没有可用的配套流程，则先在回复中补齐缺失的决策或票据图，并获得必要确认。不得把探索性问题伪装成执行批次。

完成标准：每张被排期的票据均可被独立领取；没有未解决的产品或外部契约决策被伪装成实现工作。

## 2. 锁定交付合同与事实来源

记录：

- 目标、范围、排除项及主要用户可见链路；
- issue、Agent、commit、push、部署、生产数据和外部消息的授权边界；
- 区分实现、自动验证、集成、部署、上游读回和人工/现场验收的 Done Contract；
- 当前事实、假设、未知项与外部依赖。

保持职责唯一：

- spec 或已确认计划拥有产品意图和跨票据契约；
- tracker 票据拥有交付结果、验收标准、阻塞边与 tracker 状态；
- 交付账本只拥有运行时事实：批次、负责人、模型理由、工作区所有权、门禁证据和当前阻塞项。

账本只链接这些来源，不复制完整票据内容。更新仓库惯用规划位置中的一份账本；若尚无位置且用户授权创建文件，可在适用时使用 `docs/plans/<feature-slug>-delivery.md`。使用[交付控制模板](references/plan-and-dispatch-template.md)。

完成标准：每个事实只有一个权威归属；本地完成不得被误写为部署或现场完成。

## 3. 建立可执行 frontier

票据只有在全部前置票据通过其声明的**集成门禁**后才是 `ready`（就绪），而不是 worker 返回结果后就自动就绪。

将就绪票据编入最小有效批次：

- 只并行真正独立的切片；
- 共享契约、迁移和跨模块状态机由一个明确的 integrator（集成负责人）掌管；
- 避免多个 worker 同时拥有同一文件或可变系统边界；
- 宽范围机械改动按 expand → migrate → contract 顺序推进；
- 并发只用于缩短关键路径或提供独立验收。

每个批次必须声明入口条件、票据级检查、集成门禁和停止条件。门禁失败时，下游票据继续保持阻塞。

完成标准：每张被调度的票据都已就绪、所有权不重叠，且批次具有可观察的退出门禁。

## 4. 路由模型与角色

检查当前运行时可用的模型、推理等级、角色、上下文转移限制和并发槽位。先按不确定性、爆炸半径、可逆性和反馈闭环强度路由；只有达到质量底线后，再考虑时延和成本。

- 没有具体收益时继承父 Agent 的模型；
- 不稳定契约、架构、迁移、并发、安全、外部协议和最终集成使用更强推理；
- 契约清晰且边界受控的产品切片使用均衡的 agentic 能力；
- 只读探索、机械修改、聚焦测试、清单盘点和文档使用快速或低成本能力；
- 高风险或对外可见的验收，在可用时使用不同于实现者的 reviewer 或 verifier。

每张票据记录一句模型路由理由。分配模型层级或独立角色时，读取[模型路由](references/model-routing.md)。

完成标准：frontier 中的每张票据都有负责人角色、模型决策、理由、上下文策略和验收门禁。

## 5. 确认变更边界

若用户要求先审阅或确认，先展示 frontier、批次、模型选择、门禁和未解决风险；在发布票据、修改实现代码或派发 worker 前暂停。

连续执行只授权范围内的实现流程；不自动授权 commit、push、部署、修改生产数据、发布 issue 或发送外部消息。

只有用户、仓库指令或其他适用 skill 明确允许时，才使用 subagent。

完成标准：下一次变更处于明确授权边界内。

## 6. 向每个 worker 派发一个有边界的合同

主 Agent 始终是 integrator。对每个 worker：

- 只分配一张票据或一项边界清晰的职责；
- 在代码探索后明确文件、模块或系统边界所有权；
- 提供来源链接、已完成的前置项、契约、验证命令和停止边界；
- 明确代码库由多人共享，必须保留无关修改，不得回退其他 Agent 的工作；
- 除非确实需要原始推理上下文，否则优先提供精简的新鲜上下文，而不是整个对话。

使用[交付控制模板中的派工简报](references/plan-and-dispatch-template.md)。

完成标准：每个 worker 无需猜测即可理解自己的交付结果、授权、所有权和验收测试。

## 7. 用明确状态转换监督

票据状态依次为：

`pending（待处理）→ ready（就绪）→ in_progress（执行中）→ review（审查中）→ integrated（已集成）→ external_gate（外部门禁）→ complete（完成）`

任一非终态均可转为 `blocked`（阻塞），并记录缺失的依赖、授权或证据。仅当 Done Contract 不包含部署、上游或人工验收时，才跳过 `external_gate`。

每批完成后：

1. 收集 worker 结果和实际变更文件；
2. 检查 diff 并运行票据验收检查；
3. 风险足够高时取得独立审查；
4. 按依赖顺序集成并运行批次门禁；
5. 根据实际观察到的证据更新账本；
6. 只开放新近就绪的 frontier。

不得把 Agent 的最终消息本身当作证据。不要高频轮询或播报没有变化的等待。若有票据阻塞，只继续处理独立且已就绪的工作。

完成标准：账本状态与已集成代码及观察到的检查一致；下游工作只在前置门禁通过后开放。

## 8. 按 Done Contract 收口

分别报告：

- 已实现且本地验证；
- 已集成且完成回归测试；
- 已 commit 或 push；
- 已部署且健康检查；
- 已完成上游读回；
- 已通过所需人工或现场验收；
- 已阻塞，以及确切缺失的授权或证据。

当 Done Contract 要求更强证据时，不能因为 worker 返回、本地测试通过、HTTP 请求成功或服务健康，就关闭交付。仅在已证明获授权的完成层级，或下一步需要新授权时停止。

完成标准：每个请求结果都有其声明完成层级的证据；所有剩余外部门禁均被明确标为未关闭。
