# Java 后端审查规则

只报告有代码证据支撑的问题。优先输出数量少但置信度高、且会实质影响正确性、稳定性、兼容性或可运维性的 findings。

## 严重级别

- `P0`：已确认的致命问题、数据损坏、权限或安全泄露、广泛生产风险，或语义明显错误。
- `P1`：高风险缺陷或强回归可能。
- `P2`：可维护性问题，或有合理依据但不立即致命的正确性风险。
- `P3`：值得记录但不应主导审查的优化或风格建议。

## 审查优先级

按以下顺序审查：

1. 语义和正确性
2. 空值和数据安全
3. 事务和 SQL 安全
4. 兼容性和发布风险
5. 并发和性能
6. 可观测性和可维护性

## 通用代码规则

### 重复逻辑

- 如果超过 8 行的相同逻辑出现在多个位置，且重复会增加维护风险，报告 `P2`。
- 不报告普通 setter/getter 风格的重复。

### 魔法值和硬编码

- 对枚举或状态字段的硬编码操作是 `P1`。
- 其他有业务含义的硬编码常量通常是 `P2`。
- 忽略 `0`、`1`、空字符串、明显协议常量这类无害字面量，除非它们遮蔽了业务语义。

### 空值

- 已确认的空指针解引用，或已确认某条可达路径缺少必要 guard，是 `P0`。
- 高概率空值缺陷且 guard 不完整，是 `P1`。
- 不要在没有追踪值来源时报告纯猜测 NPE。
- 遇到 `Optional.get()`、Kotlin `!!`、可空集合 `.stream()`、`Collectors.toMap` value 可空等常见 Java/Kotlin 高危模式时，读取 [nullability-gotchas.md](nullability-gotchas.md)，并在 finding 中引用对应 `NULL-*` 规则。

### 注释正确性

- 如果注释与实际行为矛盾，并暗示存在逻辑 bug，报告 `P0`。
- 如果复杂业务逻辑没有解释，且缺少注释会显著提高变更风险，报告 `P2`。

### 参数语义

- 如果实参语义和形参含义明显不匹配，例如把 `teacherId` 传给 `classId`，报告 `P0`。
- 如果命名只是模糊但不能确认错误，报告 `P2`。
- 特别关注使用同一 primitive 类型承载的不同业务 ID。

## 时间和日期规则

- 新业务逻辑应使用 `java.time` API，而不是 `java.util.Date`。新引入以 `Date` 为中心的实现是 `P0`，除非它只是边界兼容胶水。
- 代码在 timestamp、字符串、带时区时间之间转换，且业务需要 `Asia/Shanghai` 但没有显式使用时，报告 `P0`。
- 如果只是普通 `LocalDate` 或 `LocalDateTime`，没有发生时区转换，不要误报。
- 如果已有工具类正确集中处理时区，优先按安全解释。

## 数值规则

- 任何业务关键的浮点计算使用 `Double` 或 `Float` 而不是 `BigDecimal`，报告 `P0`。
- 非金融、非精度敏感的遥测或比例可以忽略，除非结果会影响持久化或用户可见业务数据。

## SQL 和 Mapper 规则

如果 diff 触及 Mapper XML、迁移 SQL、Repository 代码或查询构造逻辑，必须仔细审查 SQL。

### 硬规则

- 自定义 MyBatis XML 查询中出现 `select *` 是 `P0`。
- update/delete 没有有效 `WHERE` 是 `P0`。
- 只应更新少数字段却更新整个 entity，是 `P0`。
- 绕过参数绑定的字符串插值导致 SQL 注入风险，是 `P0`。
- 循环 SQL 是 `P0`，除非它是明确的批处理，或有边界意图的游标式分页。

### 性能和规模

- 可能超过 500 个元素的大 `IN` 条件是 `P1`，除非已经有分批。
- 无索引 join/filter、有意义表上的全表扫描、`LIMIT > 2000`、单批写入超过 1000 行、在索引过滤列上套函数，至少是 `P1`；如果代码强烈暗示生产慢 SQL，则是 `P0`。
- 如果没有 `EXPLAIN` 或 DB 元数据，把 finding 限定为静态分析风险，除非 SQL 文本已经明显错误。

### Schema 一致性

- Entity、Mapper、迁移变更不一致，且会明显破坏读写，是 `P0`。
- 如果 DB MCP 可用，升级 schema mismatch 前先确认表结构。
- 如果 DB MCP 不可用，说明数据库检查仅为静态分析。

### SQL 周围的事务形状

- 大数据集上的长事务，或读写混合循环，如果事务形状明显危险，按 `P0` 处理。
- 涉及多表或锁顺序不一致的潜在死锁模式，在代码证据充分时是 `P0`。

## Redis 规则

- 缺少 TTL 是 `P0`，除非 key 明确应该永久存在，且代码或命名能体现这一点。
- 锁 TTL 超过 1 分钟通常是 `P1`。
- 大 key 风险，例如序列化集合可能超过 1000 项，是 `P1`。
- key 命名弱或缺少前缀隔离是 `P3`。

## Spring 事务规则

- 在 Controller、Job Handler、Feign 实现或 MQ Consumer 中开启事务，是 `P0`。
- `@Transactional` 缺少 `rollbackFor` 是 `P0`。
- 隔离级别或传播行为错误且有明确业务影响，是 `P1`。
- 嵌套事务允许内层逻辑失败后外层仍提交，是 `P0`。

## MQ 规则

默认认为阿里云 RocketMQ 已处理 broker 侧持久性，审查重点放在应用逻辑。

- Producer 消息没有 key 是 `P2`。
- 消息体超过 256KB 是 `P1`。
- 业务明显需要顺序或事务消息但没有选择对应能力，是 `P1`。
- Consumer 不幂等是 `P1`。
- Consumer 逻辑缺少或弱化重试/失败处理，是 `P1`。

## 敏感数据规则

- 日志中明文手机号或身份证号是 `P0`。
- API 响应中明文手机号是 `P0`。
- 硬编码密码、key、手机号或身份证号是 `P0`。

## 兼容性规则

检查 diff 引入的破坏性变更：

- DTO/request/response 字段兼容性
- 数据库 schema 兼容性
- Redis 结构兼容性
- MQ payload 兼容性

报告口径：

- 可能导致发布中断的变更是 `P1`。
- 需要灰度、双写/双读或分阶段发布的中等兼容风险是 `P2`。

相关时，在 finding 中给出更安全的发布策略。

## 分层规则

外部接入层包括：

- Controller
- XXL-Job handler
- Feign 实现
- MQ consumer

规则：

- 外部接入层应校验输入并适配 DTO，不应直接操作 mapper/entity。
- `Mapper` 或 `Entity` 类型直接出现在外部接入层，是 `P1`。

## Feign 规则

- 没有超时、fallback 或补偿的慢下游调用会阻塞主流程，是 `P1`。
- 错误处理明显破坏流程或隐藏失败，是 `P1`。
- 循环内调用 Feign 是 `P1`，通常应建议批量 API。
- Feign 日志要足够诊断，但不能包含敏感数据或大对象。

## 日志规则

- 打印可能超过 500 项的大集合是 `P1`。
- 打印包含 `byte[]`、`char[]`、stream 或 IO 重负载 payload 的对象，是 `P1`。

## 并发规则

- 对共享可变状态缺少 JVM 内同步或并发集合，且竞态真实可发生，是 `P0`。
- 跨 JVM 共享资源可能并发写入，却缺少分布式锁或等价协调，是 `P0`。
- 线程池使用 `AbortPolicy` 是 `P1`。
- fire-and-forget 异步代码使用 `submit()` 而不是 `execute()` 是 `P1`。
- `CompletableFuture.supplyAsync()` 没有异常处理是 `P1`。
- 多个并行 future 逐个顺序 `join()`，而不是 `allOf(...).join()`，是 `P0`。

## 其他性能规则

- 线程池无界队列是 `P0`。
- 外部可写流程中的 static map/list 无淘汰增长，是 `P0`。
- 未关闭 stream 导致资源泄漏，是 `P0`。
- 锁范围过大并造成明显竞争，是 `P1`。
- 复杂 Stream pipeline 只有在明显处于 hot path 且分配开销足以造成 GC 压力时才作为 finding。

## 使用方式

- 从 diff 开始，再看所在方法，再看已解析的 1-2 跳被调用方。
- 优先具体证据，不要输出风格意见。
- 不报告缺少单元测试。这个 skill 默认不审查单元测试覆盖率。
